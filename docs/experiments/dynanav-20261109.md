## 环境与实验边界

- 主机：ROS Jazzy、Isaac Sim `6.0.1-rc.7+release.42383.32955d8d.gl`、RTX 5070 Ti。GPU 与新加卷已在主机侧确认可用。
- 场景：项目数据目录中已有的办公室 `office.usd`，机器人为项目部署的 `go2_description`。地下室碰撞修复在本次 USD 会话层实施，并记录支撑射线检查，不改原场景资产。
- 控制：RoboGauge 固定 SHA256 策略、45D 本体观测、50 Hz 策略、200 Hz 物理和 Go2HV effort；无 COM 速度 PID、无命令 slew。GT 实验采用 native pose RouteTracker，显式标记 `ground_truth_navigation=true`；新 `--slam-reference` 路径只用 live LIO 控制，单独记录其失败和限制。
- 首段路线：spawn `[-14.53, -7.5, -2.85]`，yaw 为 π，目标 `[-22.0, -7.5, -1.1441]`。参数属于隔离仿真诊断，不是生产导航配置。
- 各次运行均取当时工作树快照；实际 `capture/source_manifest.json` / `capture/source_snapshot/` 为准，最终本地提交不追溯替代运行身份。

巡航目标约 1 m/s，**没有按楼梯位置自动降速的策略**。控制器仍会按目标距离、航向误差和停车状态改变命令；“没有楼梯限速”不意味着全程保持某个实测速度。倾倒、时钟、执行器及关节速度保护继续有效。

### 1 m/s 目标与关节读回容差修正

新 [`usd-speed-100-tolerance/capture/result.json`](/media/hyh001/新加卷/6.project_data/embodied-navigation/experiments/dynanav-20261109-usd-speed-100-tolerance/capture/result.json) 以 `--speed 1 --duration 40` 运行，无楼梯自动降速，18.595 s 到达、23.615 s 停车结束。`joint_speed_peak` 记录最大读回为 **FR_calf_joint 30.000137329101562 rad/s**，比 nominal 30 高约 0.000137329 rad/s。

新 experiment 为读回比较加入 0.001 rad/s 的数值容差；引擎最大关节速度仍为 30 rad/s，Go2HV torque/envelope 保留，观测状态没有 clamp。这个结果表明 exact ≤30 的读回断言过严；修正的是数值比较，不是把电机物理上限放宽。旧运行缺失的故障瞬时读数仍未知，不能据新运行反推旧故障也是同一关节或同一幅度。

实际速度已按命令分段汇总，不能把目标值或某一段的瞬时速度写成全程恒速：

| 选段 | 时间范围 / 时长 | XY 平均 / p95 / 最大（m/s） | 3D 平均 / p95 / 最大（m/s） |
| --- | --- | --- | --- |
| 高命令巡航，`actual_command[0] >= 0.95` | 7.015–13.195 s / 6.18 s | 0.902891 / 1.034398 / 1.142689 | 0.953130 / 1.079601 / 1.144127 |
| 全部非零命令 | 7.015–18.595 s / 11.58 s | 0.629510 / 1.010004 / 1.142689 | 0.670097 / 1.057387 / 1.144127 |

高命令段的 0.95 m/s 是统计选段规则，不是新增控制阈值或楼梯限速。全部非零段包括目标附近减速，因此与巡航段平均速度不同。对应 [speed100-evidence.json](/media/hyh001/新加卷/6.project_data/embodied-navigation/experiments/dynanav-20261109-usd-speed-100-tolerance/speed100-evidence.json) 与 [summary-all-nonzero.json](/media/hyh001/新加卷/6.project_data/embodied-navigation/experiments/dynanav-20261109-usd-speed-100-tolerance/summary-all-nonzero.json) 保存原流哈希、选段规则与实测统计；完成一次首段楼梯也不证明全办公室或全部地形都能持续以该速度运行。

### 独立 gyro 四组合与采样相位审查

[审查摘要](/home/hyh001/Documents/Codex/2026-11-08/task-3/dynanav-20261109/full-route-lio-diagnosis/sdk200-phase-dt-fourway-summary.json) 与 [复现脚本](/home/hyh001/Documents/Codex/2026-11-08/task-3/dynanav-20261109/full-route-lio-diagnosis/fourway_200.py) 对同一 5.215 s 精确关键帧锚点之后的 46,041 个 SDK 样本做独立离线积分。初始真值姿态只用于评分对齐，之后没有姿态重置，也没有把该计算接入 live LIO。

| gyro 取样 / dt | 全段 SO(3) RMSE（rad） | 逐步姿态增量 RMS（rad） |
| --- | --- | --- |
| 相邻中值 / nominal 5 ms | 0.010511044 | 0.000225611 |
| 相邻中值 / SDK float32 | 0.010509287 | 0.000225611 |
| 当前右端样本 / nominal 5 ms | 0.010509779 | 0.000036201 |
| 当前右端样本 / SDK float32 | 0.010506425 | 0.000036189 |

- SDK 相邻间隔为约 4.989624–5.004883 ms。仅替换 nominal dt 时，积分姿态差异至多约 6.85e-5 rad，远小于约 0.01051 rad 的全段姿态误差；这不是 SLAM 位置误差的因果分解。
- 当前/右端 gyro 对逐步 PhysX 姿态增量的 RMS 比中值低约 6.23 倍，两次转弯分别约 11.11 / 8.37 倍，符合已记录的 post-step 取样相位。它不证明 PhysX 求解器采用某个指定积分公式。
- 四组合的长段/末端姿态误差仍几乎相等；局部步误差改善不能宣称解决 SDK 200 Hz 路线仍有的约 2.44 m 末端位置误差。
- 当前 acceleration 样本与前一物理速度增量更吻合，符合区间量测语义；相邻 body 样本取平均会改变区间语义、平滑并移相冲量。此项用 native 姿态/速度离线评分，未应用 native 初始化加速度模长归一化，不能当作 native 速度预测结果。

**没有仅凭这次离线分析改动 gyro/acc 积分相位、运行时参数、源码或二进制**。该审查已经完成，剩余定位漂移仍需其他独立实验；不能把审查发现写成已采用的 phase 修复。

## 本轮分层地图与 Agent 接口

[semantic_mapping](../../src/embodied_navigation/localization_mapping/semantic_mapping/README.md) 提供纯 CPU 的分层地图、对象 ID、历史观测、关键帧锚点修正、原子快照和查询接口；[OracleMapping](../../src/embodied_navigation/simulation/dynanav/oracle_mapping.py) 把真实采集到的深度点接入该接口。

即时 `capture/mapping/` 接入的 **位姿与像素实例分类均来自模拟器 oracle**，用于旁路诊断，不因导航改用 LIO 而自动变成估计位姿地图。独立离线重建则以实际记录的 LIO 位姿替换每个关键帧变换，`pose_source=slam`，分类仍为 `mask_source=sim_oracle`。两种图的来源分开保存，均没有运行学习分割模型。实例分类按每帧处理，语义标签刷新单独调度。

| 参数或接口 | 本轮行为 | 验证边界 |
| --- | --- | --- |
| 语义刷新 | 周期 2 s；新实例事件最短间隔 0.5 s | 本轮暂定实验参数，不是历史已经决定的模型调用频率 |

| 完整导航云 | `/dynanav/lidar_filtered` | 保留观测中的动态/未知点供障碍消费，不用静态子集替代 |

动态点与 UNKNOWN 不进入静态持久化；完整导航云保留。静态归档、对象查询和首段 live LIO 行人闭环各有对应验证；FAST-LIVO 内部几何图的全面动态污染评估、视觉动态图和完整多层导航仍需各自验收。当前视觉前端未实现动态图像掩码。

## LIO 观察器、时间原点修复与回放

本轮为 native FAST-LIVO 增加显式 opt-in 的 `ONLY_LIO` 启动路径，已单独重建并通过原生 harness 验证。默认视觉路径保留。LIO 进程只消费静态 RGB-D 点云、IMU 和 `/clock`，不消费 GT pose、不直接输出运动命令；估计输出位于 `/dynanav/lio_observer/`。默认 GT 诊断不使用它控制；显式 `--slam-reference` 模式由路线控制器消费该 live LIO，已完成下述首段/行人闭环。点云来自相机深度，不是独立激光雷达。

启动方法和依赖检查见 [LIO 配置说明](../../configs/simulation/dynanav/README_LIO.md)。现有数据将“估计器确实工作”和“定位可靠”分开：

| --- | --- |
| 运行目录 | [`dynanav-20261109-lio-stationary`](/media/hyh001/新加卷/6.project_data/embodied-navigation/experiments/dynanav-20261109-lio-stationary) |
| 实际 bag 输出 | 77 条 odom、77 条 registered cloud、76 条 TF |
| IMU 初始化 | 4.315 s 完成，304 个样本 |
| 估计漂移 | 4.415–12.015 s，约 0.67695 m |
| 结论 | 已有实际传感输入和估计输出，但不能称定位可靠 |

进一步查到 `ONLY_LIO` generic 瞬时点云的时间原点错误：RGB-D 点的零偏移相对当前帧 header，而共享 IMU 去畸变逻辑以之前传播终点为原点。修复仅在该分支的工作副本上重设偏移，不更改原始点、点序、强度或非 generic 输入；默认 LIVO 路径保留。见 [0003 patch](../../third_party/fast_livo2/patches/0003-lio-instantaneous-time-origin.patch)、[原生 harness](../../tests/native/dynanav_lio/test_lio_mode.cpp) 和 [构建入口](../../tests/native/dynanav_lio/CMakeLists.txt)。

修复后的 sensor-only 回放曾在 ROS domain 92 将同一 USD 首段楼梯 bag 的 **`/clock`、`/dynanav/lidar_static` 和 `/dynanav/imu`** 送入新 core，输出见 [`lio-usd-offset-fixed-replay`](/media/hyh001/新加卷/6.project_data/embodied-navigation/experiments/dynanav-20261109-lio-usd-offset-fixed-replay)。没有回放旧 odom/TF 或 GT pose；静态掩码仍是 oracle。随后地下室到地面层的 live LIO 记录已经用于上节实际地图重建，完整路线漂移仍未通过。

## LIO 命令闭环与量化时钟

[slam_route.py](../../src/embodied_navigation/simulation/dynanav/slam_route.py) 和 [build_dynanav_slam_route.py](../../scripts/build_dynanav_slam_route.py) 提供 `--slam-reference` 模式。参考路线从之前实际 LIO 记录提取，当前路线位姿与命令只使用 live LIO，`ground_truth_navigation=false`；GT 仍用于本体观测、物理检查、诊断归档和离线评分，不能把这些其他用途误写成导航用了 GT。

该模式有明确的 **repeat-spawn 实验室假设**：用当前首个就绪的 LIO 位姿与先前记录的测量锚点对齐。没有全局地图配准、任意初始位置定位或通用重定位能力；`map_registration_enabled=false`。参考见 [slam-reference.json](/media/hyh001/新加卷/6.project_data/embodied-navigation/experiments/dynanav-20261109-slam-route-repeat-spawn-reference/slam-reference.json)。

首次 [`slam-route/capture/result.json`](/media/hyh001/新加卷/6.project_data/embodied-navigation/experiments/dynanav-20261109-slam-route/capture/result.json) 已实际使用 LIO 驾驶，但最终 `corner_brake_timeout`、`arrived=false`。33 次 `future_odometry` 来自 SDK float32 header stamp 比同一步物理时间超前约 2.441 μs，超过该次接入的 2 μs 容差，导致 pose speed window 被清空。

后续容差设计按运行 horizon 的 float32 half-ULP 加 1e-7 s 数值余量确定，而不是放宽正常里程计新鲜度。100 s horizon 对应约 3.914697 μs。首个 [`slam-pedestrian-clock-fixed`](/media/hyh001/新加卷/6.project_data/embodied-navigation/experiments/dynanav-20261109-slam-pedestrian-clock-fixed) 尝试实际又遇到构造器残留 2 μs 硬上限，启动时即抛出 ValueError，尚未发布传感帧；因此不能写成已跑通时钟修正后的行人 SLAM。这个启动失败保留；构造器已改为要求 `future_tolerance_s < max_sim_age_s`，默认 2 μs 不变。新 factory 的 `--check` 与 live loop 构造同一控制器，horizon 推导的 3.914697 μs 已在下面的实际成功运行中传入，不再被残留上限挡住。

当前停止速度来源选择 0.5 s 的估计 pose window。参考终点的 reported twist 约 0.081 m/s，与姿态窗口中的低位移不一致；此矛盾保留为未解决的估计限制。窗口净位移还可能抵消振荡，不能据此宣称速度或停车估计可靠。

### 同输入重采：两次 SDK 中止后停止重试

第一次补救重采使用 [`dual-stairs-paired`](/media/hyh001/新加卷/6.project_data/embodied-navigation/experiments/dynanav-20261109-dual-stairs-paired)：ROS domain 104 中，同一 capture 同时供给 LIO 与 LIVO，分别输出在 `/dynanav/lio_comparison`、`/dynanav/livo_comparison`，二者均使用新 lifetime core。各自 ingress、处理覆盖、post-VIO 状态、共同前缀误差与资源已完成最终核验，见下表及 [最终前缀审计](/media/hyh001/新加卷/6.project_data/embodied-navigation/experiments/dynanav-20261109-dual-stairs-paired-retry/final-audit/paired-prefix-final-audit.json)；它不使未完成的全路线 A/B 变成通过。
